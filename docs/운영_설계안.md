# HR 운영 리포트 — 실제 운영을 위한 저장 · 인증 · 권한 설계안

> 현재 배포본은 **가상 데이터 기반 로컬 데모**입니다. 이 문서는 실제 회사에서 쓰려면 무엇을 더 만들어야 하는지 정리한 설계안이며, 아직 구현되지 않았습니다.

## 1. 현재 구조 (코드에서 확인한 사실)

| 항목 | 현재 |
|---|---|
| 인증 · 로그인 | 없음 |
| 권한 | 없음 — URL을 아는 누구나 같은 화면 |
| 서버 함수 | `api/ask` 하나 (자연어 → SQL 생성, Gemini 호출). 인사 데이터 · 조치 기록을 받거나 저장하지 않음 |
| 인사 데이터 처리 | 브라우저 안 DuckDB-WASM. 업로드 파일은 서버로 전송하지 않음 |
| 조치 기록 · 검토 기준 | 브라우저 `localStorage` (`hr.actions.v1` · `hr.criteria.v1` · `hr.firstSeen.v1`) |
| 수정 이력 | 같은 브라우저 안의 로그 배열 — 누구나 지우거나 고칠 수 있음 |

따라서 지금의 조치 기록은 **회사의 조치 이력으로 인정될 수 없습니다**: 담당자 본인 확인이 없고, 다른 PC와 공유되지 않으며, 브라우저 데이터를 지우면 사라집니다.

## 2. 운영 구조

```
[사내망 브라우저] ──SSO 로그인──▶ [사내 API 서버] ──▶ [사내 DB (PostgreSQL)]
        │                              │
        │ 집계 · 탐지 결과 조회           ├─ 인사 원본 적재(배치, 인사 시스템 연동)
        │ 조치 기록 입력                  ├─ 탐지 배치(기준 버전별 실행 · 결과 스냅샷)
        ▼                              └─ 감사 로그(추가만 가능)
  원본 행 · 개인 급여는 권한 있는 화면에서만
```

- 원본 인사 데이터는 사내망 DB에만 두고 공개 배포하지 않습니다.
- 탐지는 서버 배치로 실행하고, 실행 시점 · 기준 버전 · 데이터 기준월을 함께 저장합니다(재현 가능).
- 자연어 질의를 계속 쓴다면, 외부 AI로 나가는 내용(질의 · 테이블 구조 · 집계 결과)을 정책으로 정하고 사번 등 식별자 값은 가립니다.

## 3. 테이블 설계 (요지)

| 테이블 | 주요 컬럼 | 비고 |
|---|---|---|
| `criteria` | criteria_id, name, type(운영/통계적 탐지/데이터 검증), metric, compare, target | 기준의 정의 |
| `criteria_versions` | criteria_id, version, params(json), start_date, is_pilot, reason, changed_by, changed_at | 추가만 가능. 기준 변경 = 새 버전 |
| `detection_runs` | run_id, data_month, data_snapshot_id, started_at, criteria_versions(json) | 탐지 실행 단위 |
| `review_items` | item_id, run_id, rule, target_type, emp_id/org_id, period, threshold, actual, diff, reason, criteria_version | 탐지 결과 스냅샷(이후 데이터가 바뀌어도 그대로) |
| `actions` | item_id, owner_user_id, status, cause, need_action, action_text, planned_date, done_date, followup_date, close_reason, final_basis, evaluation | 현재 상태 |
| `action_events` | event_id, item_id, user_id, at, field, before, after | **추가만 가능**(UPDATE · DELETE 권한 없음) — 감사 추적 |
| `followups` | item_id, before_value, after_value, after_period, recurrence, checked_by, checked_at | 후속 점검 결과 |

## 4. 인증 · 권한 모델

| 역할 | 할 수 있는 일 | 할 수 없는 일 |
|---|---|---|
| HR 관리자 | 기준 변경(사유 필수), 항목 배정, 종결 승인, 전체 열람 | 감사 로그 수정 |
| HR 담당자 | 배정된 항목의 조치 기록 · 상태 변경, 근거 열람 | 기준 변경, 남의 항목 종결 |
| 조직장 | 자기 조직의 **집계 지표** 열람 | 개인별 근태 원본 · 급여 열람 |
| 감사 | 전체 읽기 전용, 감사 로그 열람 | 모든 쓰기 |

- 인증: 사내 SSO(OIDC 또는 SAML). 담당자 · 변경자는 로그인 사용자 ID로 서버가 기록(입력값으로 받지 않음).
- 개인별 급여 금액은 별도 권한(급여 담당)에서만 조회. 대시보드 · 검토 목록에는 집계만.
- 행 수준 보안: 조직장은 자기 조직 행만, HR 담당자는 담당 범위만.

## 5. 운영 원칙

- 검토 항목은 **확인할 근거**이며 위반 판정이 아닙니다. 상태 변경 · 종결은 사람이 하고, 시스템은 원인을 확정하거나 조치를 자동 집행하지 않습니다.
- 근태 변화만으로 업무 태도 · 성과 · 건강 · 퇴사 가능성을 판단하지 않습니다. 이 기록을 성과평가 · 인사상 불이익의 근거로 쓰지 않도록 이용 정책에 명시합니다.
- 시범 기준은 회사가 공식 확정하기 전까지 '시범'으로 표시하고, 확정 시 승인자와 근거 문서를 버전에 남깁니다.
- 개인정보: 수집 목적 · 보존 기간 · 파기 절차를 정하고, 로그(서버 · 프록시 · AI 호출)에 사번 · 급여 · 업로드 파일 내용 · API 키를 남기지 않습니다.

## 6. 실제 HR 운영에 추가로 필요한 데이터

| 데이터 | 쓰임 |
|---|---|
| 조직 이동 이력(발령일 · 이전/이후 부서) | 과거 월의 실제 소속 기준 부서 분석 |
| 근무 일정 · 휴일 · 휴가 · 휴직 기록 | 근무 기록이 없는 날의 사유 구분, 근무일수 보정 |
| 초과근로 신청 · 승인 기록 | 승인 절차 점검, 사전 승인 없는 초과근로 확인 |
| 근로시간 관련 사내 규정 · 법정 기준(확인된 값) | 시범 기준을 확정 기준으로 전환 |
| 프로젝트 · 업무 배정, 업무 집중 기간 | 초과근로 증가의 맥락 확인 |
| 급여 지급 기준표 · 지급 사유 코드 | 지급액 급변의 원인 확인 |
| 퇴사 면담 결과(구조화된 사유) | 퇴사율 원인 검토 |
